# Controlling TRE Data Access

## Prerequisites

- TRE agent deployed
- Access to the TRE UI
- TRE admin credentials
- TRE data source connection details
- Knowledge of how the TRE grants access to its DB

## Configuring DMN Rules

Log in to the TRE Layer UI and navigate to the “DMN Rules” section.

This page helps to set the values which are used by the TES backend (e.g., Funnel) to connect to the TRE DB using short-lived, ephemeral credentials rather than static, long-lived ones - reducing the risk of credential leakage or reuse.

![DMN Rules screenshot](/images/tre-layer/DMNRules.png)

Each Postgres connection used by a project is identified by its own `tag` value in the DMN table. Find the `postgresDatabase`, `postgresServer` and `postgresPort` rows for each connection tag the project uses and set them to match the TRE's database credentials.

| Output:env       | Output:value                       |
| ---------------- | ---------------------------------- |
| postgresDatabase | change to the TRE DB database name |
| postgresServer   | change to the TRE DB host          |
| postgresPort     | change to the TRE DB port          |

<Callout type="info">
  - 5S-TES has been tested and confirmed working with Postgres. Trino and S3 are
  supported in principle but not yet fully verified.
  - More details about TRE DB can be found [here](/explanations/how-5s-tes-works/tre-agent#tre-database).
</Callout>

### Configuring schema access

Each Postgres connection can be granted access to one or more schemas, and the permissions for each schema are configured independently. For every schema, add two rows sharing the same connection tag:
  - One must have an `env` name containing the word `schema` plus an identifier, e.g. `schemaAnalytics`. Its value should be set to the name of the schema.
  - The other must be a matching row with an `env` name containing the word `permissions`. This must be given the same identifier as the schema (e.g. `permissionsAnalytics`) and should have comma-separated permissions as its value, e.g. `Read,Write,CreateTables`. 
Every `env` name must include an identifier, otherwise we cannot match schemas to their levels of permission. If no permissions row is found or the permissions value is left empty, the schema defaults to readonly access.

| Permission       | Description                                           |
| ---------------- | ----------------------------------------------------- |
| Read             | Select on all tables in the schema                    |
| Write            | Insert, Update, Delete on all tables in the schema    |
| CreateTables     | Create new tables or objects in the schema            |

<Callout type="warning">
  Adding or deploying these rules only ensures the schema itself exists — it never creates tables inside it. Either grant `CreateTables` so a submission can create its own tables, or have an admin create the expected tables in advance.
</Callout>

#### Example

A project with a read-only source connection and a separate writable scratch connection might look like this:

| Output:tag         | Output:env           | Output:value                   | 
| ------------------ | -------------------- | ------------------------------ |
| `postgres-source`  | `schemaSource`       | `string(project)`              |
| `postgres-source`  | `permissionsSource`  | `"Read"`                       |
| `postgres-scratch` | `schemaScratch`      | `string(project) + "-scratch"` |
| `postgres-scratch` | `permissionsScratch` | `"Read,Write,CreateTables"`    |

### Notices
- Any string value put into an output value should be inside double quotes. For example: `"public"`. If the output values refer to input variables, double quotes are not required, for example, `string(project)`. See [Camunda DMN rule convention](https://docs.camunda.io/docs/components/modeler/feel/language-guide/feel-expressions-introduction/) for more details.
- If a schema holds the [OMOP CDM](/explanations/concepts/omop), its value must hold the actual lowercase schema name in double quotes.
